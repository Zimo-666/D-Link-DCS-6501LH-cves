# [CVE-TBD] D-Link DCS-6501LH V3.03.02 Unauthenticated Stack Buffer Overflow in StreamProxy Content-Length Parsing

## VulDB Submission Fields

- Vendor: D-Link
- Product: DCS-6501LH (DCS6501LHCx)
- Version or Commit: V3.03.02 (firmware package DCS6501LHCx_FW303B02_SD)
- Vulnerability: Stack-based Buffer Overflow (CWE-121)
- Advisory / Exploit URL: https://github.com/Zimo-666/D-Link-DCS-6501LH-cves/tree/main/05-streamproxy-content-length-header-overflow
- Description:

```
A stack-based buffer overflow vulnerability was discovered in D-Link DCS-6501LH camera firmware v3.03.02. The mydlink StreamProxy listener on TCP port 7000 (plaintext HTTP) routes requests that carry a Content-Type header to GetContentlen (0x004A3820 in aoni_ipc), which tokenises the request by CRLF and copies the remainder of the Content-Length header line into a 32-byte stack buffer with strncpy(), using the line length minus 16 as the count and never bounding it to the destination size. The frame is 80 bytes, the buffer is at sp+24 and the saved return address at sp+76, only 52 bytes above it, so a Content-Length header line longer than 68 characters overwrites the saved registers and the return address, and no authentication is involved. Reproduction: send the POST request generated by poc.py (Content-Type header plus a Content-Length line padded with 200 'A' characters) to port 7000; the daemon crashes with pc = ra = 0x41414141 in an emulated run of the stock binary, while an 8-byte padding leaves the service running. Impact: unauthenticated remote code execution in the camera daemon running as root, demonstrated as instruction-pointer control with a crash-only payload. This is a distinct defect from the Content-Length body copy in the same listener: it depends on the header line length rather than the numeric value and requires its own fix. Proposed CVSS:3.1/AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H (8.8).
```

## Technical Disclosure

### Summary

The device starts a mydlink StreamProxy listener on TCP port 7000 during the
normal boot sequence. The listener speaks plaintext HTTP and hands each
connection to `ExecuteOneAccept`. When the request contains a `Content-Type`
header, that handler calls `GetContentlen`, which walks the request line by
line and, on the `Content-Length: ` line, copies the rest of the line into a
32-byte stack buffer without bounding the size. Because the saved return
address is only 52 bytes above the buffer, a long header line gives the
attacker control of the instruction pointer.

### Affected Product and Firmware

- Vendor: D-Link
- Product: DCS-6501LH (DCS6501LHCx), indoor network camera
- Firmware: V3.03.02, package `DCS6501LHCx_FW303B02_SD.bin`
  (image 16,025,960 bytes, sha256
  `8751e1219ddfd839f59a3b01b2ecace2ecf3c9b95cc83f8278886bc87e0652c1`)
- Application build: `AONI_IPC Make On Aug  4 2025 18:08:26 V3.03.02`
- Platform: Ingenic T31, MIPS32 little-endian, Linux 3.10.14

### Vulnerability Details and Root Cause

`GetContentlen` at `0x004A3820`:

```c
char dest[32];
...
v2 = strtok(a2, "\r\n");
while (v2) {
    v4 = strlen(v2);
    if (!strncmp(v2, "Content-Length: ", 0x10u)) {
        strncpy(dest, v2 + 16, v4 - 16);   /* dest[32], unbounded */
        return strtol(dest, 0, 10);
    }
    v2 = strtok(0, "\r\n");
}
```

Prologue:

```
004a3820:  addiu sp,sp,-80
004a3824:  sw    ra,76(sp)
```

`dest` is at `sp+24`; `ra` is at `sp+76`, 52 bytes above the start of the
buffer. Any `Content-Length: ` line longer than 68 characters produces a copy
larger than 52 bytes and overwrites the saved return address.

### Vulnerable Component, Function and Call Chain

- Component: mydlink StreamProxy in `aoni_ipc`
- Listener: `HttpServer_FUN` (`0x004A34B8`), TCP 7000 (`0x1B58`)
- Handler: `ExecuteOneAccept` (`0x004A38FC`) -> `GetContentlen`
  (`0x004A3820`), copy at `0x004A38B4`
- Start condition: default boot path (`pf_mydlink_init`)

### Authentication Requirements and Attack Conditions

- No authentication: plaintext HTTP, the copy happens before any credential
  handling.
- Network reachability to TCP port 7000 (local network by default, internet if
  forwarded).
- No user interaction and no configuration change are required.

### Proof of Concept and Reproduction

The PoC is `poc.py` in this directory. It sends a single POST request whose
`Content-Length` line is padded with 200 characters:

```bash
python3 poc.py <host> [port]
```

A benign reference request with 8 characters of padding, identical otherwise,
is available with `python3 poc.py <host> [port] --control`. Expected result on
a vulnerable device: the connection is closed without an HTTP response and the
daemon crashes with the instruction pointer set to `0x41414141`; the benign
request leaves the service running.

Observed under GDB with the stock binary:

```
Thread 2 received signal SIGSEGV, Segmentation fault.
#0  0x41414141 in ?? ()
pc: 0x41414141   ra: 0x41414141
```

### Observed Results and Evidence

| Content-Length line padding | bytes copied | result |
|---|---|---|
| 8 | 24 | connection reset, process alive |
| 40 | 40 | SIGSEGV |
| 200 | 200 | SIGSEGV, `pc = ra = 0x41414141` |
| 800 | 800 | SIGSEGV |

The 0x41 fill appears in the program counter and return address, demonstrating
direct instruction-pointer control.

### Security Impact

Unauthenticated remote code execution potential: the daemon runs as root, the
affected frame has no stack canary, and the attacker controls the overwritten
return address and saved registers. The PoC is a crash-only demonstration; no
shell was spawned.

### CWE and CVSS

- CWE-121: Stack-based Buffer Overflow
- CVSS:3.1/AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H (8.8)

### Related CVEs and Novelty

The published issues for this firmware version are CVE-2026-125079 (hard-coded
credentials in `SystemConfig.ini`) and CVE-2026-113735 (weak credential in
`mydlink_set_root_pwd`). Four other memory-safety issues were reported
separately for this product: a heap overflow in the RTSP request parser, an
invalid free and a stack overflow in RTSP digest handling, and a stack
overflow caused by the numeric `Content-Length` value in `ExecuteOneAccept`
on the same port. The present issue is a different defect in a different
function (`GetContentlen`), triggered by the length of the header line rather
than by the numeric value, reached only when a `Content-Type` header is
present, and fixed independently.

### Suggested Remediation

- Bound the copy to `sizeof(dest) - 1` and NUL-terminate the result, or parse
  the digits in place without copying.
- Reject requests whose header lines exceed a sane protocol limit.
- Build with stack protector and fortify sources enabled.
